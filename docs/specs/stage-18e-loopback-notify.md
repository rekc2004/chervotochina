## 1. Тесты слушают только петлю (КРИТИЧНО)
Проблема: каждый пересобранный тестовый бинарник (имя с хешем) открывает UDP на `0.0.0.0`, Windows спрашивает «Разрешить доступ» → десятки окон у владельца при каждом прогоне тестов (накопилось ~260 правил).

Места: `crates/chervo-core/src/node/mod.rs:461` (сокет узла, `0.0.0.0:port`), `mod.rs:174` (`pick_port`, проба на `0.0.0.0`); `NodeConfig` (mod.rs:96-102) адреса привязки не имеет. LAN: `crates/chervo-lan/src/net.rs:71` (продукт `0.0.0.0:LAN_PORT` на Windows; в тестах уже `TestNet { bind, .. }` за feature `test-net`). Время: `crates/chervo-timesync/src/lib.rs:211` (`0.0.0.0:0` + connect). Пробы: `crates/chervo-addr/src/probe.rs:32,47-64` (bind+connect, без слушания).

Нужно:
- В `NodeConfig` адрес привязки сокета узла, **доступный только тестам**: поле или метод за `#[cfg(any(test, feature = "test-net"))]` (имя feature — как принято в репозитории; если для chervo-core нет подходящей — завести `test-net` в chervo-core, включать только в dev-dependencies тестов). В обычной сборке (GUI, CLI, релиз) поля нет вовсе — продукт всегда `0.0.0.0` как сейчас. `pick_port` проверяет порт на том же адресе, на котором узел будет слушать.
- Все тестовые помощники, создающие узел (`crates/chervo-core/tests/support/harness.rs:194-217` и прочие из 32 файлов с `Node::` в tests/, CLI-тесты `repl_two_nodes_scripted` и др.), ставят `127.0.0.1`. Адреса друзей в тестах и так петлевые — проверить, что ничего не ломается (подключение к 127.0.0.1 узла, слушающего 127.0.0.1).
- Тесты, которым нужен второй адрес петли или 0.0.0.0 (`chervo-transport-quinn/src/tests/echo.rs:232,237`, `preauth.rs:148-150`, `race.rs:119`, `chervo-upnp` fake_igd, `chervo-lan` svc.rs) — оставить как есть, но если они слушают `0.0.0.0`, по возможности перевести на конкретный петлевой адрес (127.0.0.x тоже петля и запроса не вызывает). Что перевести нельзя — перечислить в отчёте с причиной.
- timesync и probe: если в тестах они делают bind на `0.0.0.0` — тестам дать петлевой адрес тем же способом (cfg/feature), продукт не менять.
- Критерий (обязательно, Windows): до и после прогона `cargo test --workspace --locked` на этом компьютере сосчитать правила брандмауэра на программы из каталога сборки (`Get-NetFirewallRule | Get-NetFirewallApplicationFilter` с путём в target-каталоге) — новых правил не появилось, и при прогоне не открывалось окно брандмауэра (если тестовый бинарь всё же слушает не-петлю, Windows создаёт правило/окно — это и есть проверка). Если окно появилось — перечислить, какой тест.
- Страж: тест или скрипт, который ловит `UNSPECIFIED`/`0.0.0.0` в тестовых помощниках узла (простая проверка исходников), чтобы новый тест не вернул проблему. Описать эвристику.

## 2. Оповещение ОС о входящем файле (решение владельца 2026-11-20, закрывает отложенный D7/Q6 этапа 18 в части уведомлений)
Сейчас: только мигание в панели задач (`chervo-gui/src/main_model.rs:287` `take_attention`, `app.rs:114-116` `RequestUserAttention`).

Нужно (Windows обязательно; Linux и macOS — если дёшево, иначе оставить мигание и записать):
- При новом входящем предложении, которое ждёт ответа (не автоприём), — системное уведомление: заголовок «Червоточина», текст «{друг} прислал файлы: {N} шт., {размер}» (одно имя файла можно показать, если файл один). При автоприёме — уведомление «{друг}: файлы приняты» по завершении. Не чаще одного уведомления на предложение.
- По щелчку на уведомление — окно программы выходит вперёд на вкладке «Файлы» (если это достижимо без лишних зависимостей; иначе достаточно уведомления, записать).
- Имена друга и файлов — недоверенный ввод: обрезать по длине (например 64 символа), убрать управляющие символы и переводы строк, не интерпретировать как разметку (для Windows toast XML — экранирование; предпочтительно API без XML).
- Зависимости: **без новых крейтов по возможности**. Windows: `windows-sys 0.61.2` уже в Cargo.lock — допустимо добавить прямую зависимость на эту же версию с нужными features (например `Win32_UI_Shell` для `Shell_NotifyIconW` с `NIF_INFO`; на Windows 10/11 такое уведомление показывается как обычное системное). Значок в области уведомлений, если нужен для API, — временный, без меню, убирается после уведомления или при выходе. Если без нового крейта невозможно — остановиться и описать варианты (крейт, версия, лицензия, дерево зависимостей) для решения владельца; ничего не добавлять.
- Linux: можно через существующий D-Bus (zbus 6 уже используется в `chervo-identity`, разрешён `scripts/check-gui-linux-tree.sh`), `org.freedesktop.Notifications.Notify`. Если это тянет запрещённое в дерево GUI — не делать, записать.
- macOS: мигание в Dock (уже есть) — достаточно.
- Настройка «Уведомлять о входящих файлах» в «Настройках» (галочка с «?», по умолчанию включена).
- Тесты: модель решает «показать уведомление» один раз на предложение; санитизация текста (управляющие символы, длина, XML-символы); при выключенной настройке — не показывает.
