1. **Код** (в `spikes/transport/`, тот же отдельный workspace). Новый бинарник `spike8` (`src/bin/spike8.rs`) и модули `src/xfer.rs` (передача и докачка), `src/natp.rs` (зонд, отражатель, посредник). Свой адаптер `Conn` для quinn скопировать из `spike-b.rs` (≈40 строк), ключ сервера одноразовый через `tlsb::ephemeral_server` на каждое входящее через `accept_with`, клиент `tlsb::client_tls`, аутентификация `auth::{caller_auth, callee_auth}` без изменений. Лимитера по IP и Retry в `spike8` нет (не предмет замера). Единственная новая зависимость: `igd-next = "=0.18.0"` (фичи по умолчанию). Хэшей в коде нет: сверка файлов `cmp` и `sha256sum` в скрипте.
2. **Протокол передачи** (`xfer.rs`, после `auth_ok`). Звонящий открывает управляющий bi-поток и шлёт `XFER1` или `HELLO1`. На `XFER1` вызываемый отвечает `RESUME` (принятое по каждой доле из памяти процесса по `id`; новый `id` = нули), отправитель открывает `streams` uni-потоков, по одному на долю, начиная с принятого; доля `i` = `[i*size/n, (i+1)*size/n)`; получатель пишет `FileExt::write_at`, по завершении всех долей шлёт `DONE`, отправитель закрывает соединение кодом 0. Обрыв: отправитель перебирает адреса `--connect` по кругу (попытка 3 с) до `--reconnect-deadline-s`, новое соединение, та же аутентификация, тот же `id`, `RESUME`, продолжение. На `HELLO1` вызываемый отвечает `OBS` (свой `conn.remote_address()`) и закрывает.
3. **Стенд части 1** = стенд этапа 7 вызовом `bash run.sh setup b` / `teardown b` (не править `run.sh`). Отправитель (клиент) в `chv-a`, получатель (сервер) в `chv-b`. LO: оба в `chv-b`, 127.0.0.1. L0: LAN 10.77.0.2→10.77.0.3 (мост, без netem). R1-R4: маршрут 10.77.1.2→10.77.2.2 через `chv-r`. В `chv-r` выключить offload на `ra rb la lb` (`ethtool -K <if> gro off gso off tso off`), иначе netem теряет пачки GSO целиком [В]. netem в `chv-r`: на `rb` (данные к получателю) `delay D rate R limit L [loss P]`, на `ra` (ACK) `delay D rate R limit L`.
4. **Стенд NAT (части 2-5)**, все ns с префиксом `chv8-`, имена интерфейсов ≤ 15 символов. `CORE` = переменная, по умолчанию `198.51.100` (TEST-NET-2). `chv8-i`: мост `core0`, без адреса. На ядре: `na` wan `CORE.10`, `na2` `CORE.20`, `nb` `CORE.30`, `cg` `CORE.40`, `w` («белый IP», стационарный ПК) `CORE.50`, `m` (отражатель и имитация посредника) `CORE.100` и `CORE.101`. За NAT: `na` lan 192.168.10.1/24 (мост) ← `ha` 192.168.10.2 (ноутбук; второй интерфейс `eth1` 192.168.20.2 к `na2` lan 192.168.20.1, выключен) и `ha2` 192.168.10.3; `nb` lan 192.168.30.1 ← `hb` .2; `cg` in 100.64.0.1/10 ← `nc` wan 100.64.0.2/10, lan 192.168.40.1 ← `hc` .2. Выхода наружу нет; DNS-заглушка как в этапе 7. Сокет приложения всегда UDP 4433 (у `ha2` 4434).
   **Правила NAT** (на `na`, `na2`, `nb`, `nc`, `cg`; `L` = lan-подсеть, `H` = внутренний хост:порт). Общее: `table ip nat8 { chain pre {type nat hook prerouting priority dstnat;} chain post {type nat hook postrouting priority srcnat; oifname "wan" ip saddr L <MASQ>} chain fwd {type filter hook forward priority filter; policy drop; iifname "lan" oifname "wan" accept; iifname "wan" ct state established,related accept; iifname "wan" ct status dnat accept} chain inp {type filter hook input priority filter; iifname "wan" drop} }`. `inp` нужен: пакет снаружи до своего исходящего иначе создаст на NAT запись conntrack и сломает сохранение порта [В, НП]. Типы:
   - PR (EIM, фильтр адрес+порт): `<MASQ>` = `masquerade` (порт сохраняется, если свободен) [В].
   - AR (EIM, фильтр по адресу): PR + `set seen {type ipv4_addr; flags dynamic,timeout; timeout 120s}`, в `fwd` перед accept `iifname "lan" udp sport 4433 update @seen { ip daddr }`, в `pre` `iifname "wan" udp dport 4433 ip saddr @seen dnat to H`.
   - FC (EIM, EIF, full cone): PR + в `pre` `iifname "wan" udp dport 4433 dnat to H`. Это эквивалент проброса порта для одного сокета, а не общий full cone [В]; так и пометить.
   - SYM (EDM): `<MASQ>` = `masquerade fully-random` [НП синтаксис].
   - CG: `cg` с PR (CG-EIM) или SYM (CG-SYM), за ним `nc` с PR (двойной NAT: домашний роутер в 100.64.0.0/10). Отдельной строки «двойной NAT 10.x» нет: поведение NAT от диапазона не зависит [В], диапазон влияет только на классификацию (G5.5, G6).
   - Hairpin не эмулируется: строка G4 «оба за одним NAT по внешним адресам» это отрицательный случай.
   Перед каждой попыткой: перезагрузить набор правил и `conntrack -F` во всех NAT-ns (свежее состояние).

## Интерфейс (точно)
Подкоманды `spike8`: `keygen --dir D`; `recv --listen ip:port --pairs D --out-dir DIR --max-bytes N [--win W0|W1] [--cc cubic|bbr] [--idle-s S] [--keepalive-s S]`; `send --connect a1[,a2..] --pairs D --pair 1|2 --file F [--streams 1..16] [--win] [--cc] [--idle-s] [--keepalive-s] [--local ip:port] [--reconnect-deadline-s S]`; `hello --connect A --local ip:port --pairs D --pair N`; `punch --local ip:port --peer ip:port --pairs D --pair N --mode periodic|sync [--rdv ip:port --tag hex16 --side 1|2] [--interval-s 5 --attempt-s 10 --deadline-s 40]`; `reflect --bind a,b,c`; `natprobe --local ip:port --r1a A --r1b B --r2 C`; `rdv --listen ip:port`; `upnp map|unmap|info --internal ip:port --ext-port P [--lease S]`.
Сообщения (big-endian; `M` = `"CHX8"`, версия 0x01): `XFER1 = M|01|01|id[16]|size u64|streams u8` (30 Б); `HELLO1 = M|01|02` (6); `RESUME = M|01|03|n u8|n×u64`; `OBS = M|01|04|04|ip[4]|port u16` (13); `DONE = M|01|05|total u64` (14); заголовок потока данных `slice u8|offset u64|len u64` (17). Зонд: запрос `"CHP8"|cmd u8|nonce[8]` (13; cmd 1 эхо, 2 ответ с R1b, 3 ответ с R2), ответ `"CHP8"|cmd|nonce[8]|ip[4]|port u16` (19). Посредник: `REG = "CHR8"|tag[16]|side u8` (21), `GO = "CHR8"|ip[4]|port u16|delay_ms u16` (12). Ничего иного `rdv` не принимает и не пересылает.
События (формат этапа 7, `EVENT <имя> t=<мс> k=v`): `xfer_start id size streams resume_from`, `xfer_progress bytes` (каждые 250 мс), `xfer_done bytes ms conns`, `send_done app_bytes_sent conns`, `reconnect n after_ms`, `peer_addr_change old new`, `qstats rtt_ms min_rtt_ms cwnd lost_packets sent_packets congestion_events mtu`, `cpu_ticks phase=start|end ticks`, `observed_by_peer addr`, `nat_probe mapping filtering ext`, `punch_ok dir ms`, `punch_fail reason`, `upnp_gateway|upnp_ext_ip|upnp_mapped|upnp_unmapped|upnp_error`.

## Недоверенный ввод
Все сообщения выше разбираются с проверкой длины до среза, неизвестный magic/версия/тип = закрытие без паники; `size ≤ --max-bytes`, `1 ≤ streams ≤ 16`, `slice < n`, `offset` равен началу доли + принятое, `offset + len` равно концу доли (сложение с проверкой переполнения); управляющий поток читается с лимитом 64 Б и тайм-аутом 5 с; `unwrap`/`expect` на сетевых данных запрещены. UDP-службы (`reflect`, `rdv`) отвечают только на сообщения точной длины, `rdv` держит не больше 16 регистраций. Ответы шлюза разбирает igd-next.
