## 2. Выбор

### 2.1. Форк или с нуля
**Сборка с нуля поверх библиотек, без форка приложений-аналогов** [В]. Причины: требованиям 1-2 по документации соответствует только LocalSend, но он только для LAN, на Flutter/Dart, с HTTP API и TLS-сертификатом устройства, а не QUIC (раздел 1); остальные по умолчанию держатся на relay, DHT, серверах обнаружения или публичном STUN, их пришлось бы вырезать из ядра соединения; форк потянул бы чужую модель relay и обнаружения, которую пришлось бы удалять, и это риск оставить скрытый путь к чужому серверу (у DashBeam обнаружение через n0 в приложении не отключается [П-р]); ближайший по архитектуре DashBeam под AGPL-3.0-only [П-р], форк или заимствование кода навязали бы лицензию до решения владельца (U17, U21).

### 2.2. QUIC и аутентификация: TLS 1.3, не Noise
- QUIC несёт TLS 1.3 штатно (RFC 9001), forward secrecy через эфемерный ECDHE [В]. Noise поверх QUIC нестандартен, `snow` 0.10.0 не обновлялся с 2025-07 [П-р]. Значит TLS 1.3 с raw public keys (RFC 7250) и пиннингом Ed25519-ключей друзей.
- 0-RTT не использовать (нет forward secrecy для ранних данных и есть replay) [В]. Возобновление сессий по тикетам тоже отключить, пока не проверено, что оно идёт только в режиме psk_dhe_ke [Д по rustls, не проверено].
- **Поправка по U10b (решение владельца 2026-10-09).** TLS 1.3 остаётся, но ключ TLS одноразовый, новый на каждое соединение, и друзьями не пиннится. Подлинность даёт подпись ключом пары над экспортёром TLS внутри уже зашифрованного канала (2.6). Пункт про 0-RTT и тикеты в силе.

### 2.3. Кандидаты

**A. iroh 1.3.0 через `Builder::empty()` + пресет `Minimal`** (только крипто-провайдер).
Что видно в исходнике [П]:
- `Builder::empty()`: пустой список address lookup, relay выключен (транспорт relay не создаётся), только IPv4/IPv6 UDP (`src/endpoint.rs:192-222`, `:155-158`). `Builder::new(preset)` = `empty().preset(preset)` (`:182-184`). Значит все внешние службы приходят из пресета `N0`, их можно не включать. Документация это подтверждает: «Creates an empty builder with no address lookup services, and RelayMode::Disabled» (docs.rs/iroh/1.3.0, `Builder`) [П-р].
- Проверка captive portal и HTTPS/QAD-пробы net_report ходят только к relay из relay map (`src/net_report/reportgen.rs:287-289`, `:593`, `src/net_report/options.rs:62-75`). При пустой карте relay целей у них нет [В по коду, не запускалось].
- Адрес пира задаётся явно: `EndpointAddr { id, addrs }`, где `addrs` содержит `TransportAddr::Ip(SocketAddr)` или `Relay(url)` (`src/socket/remote_map.rs:316`, `src/endpoint.rs:1295-1300`). Если прямые адреса даны, они используются без relay (документация `connect`, `src/endpoint.rs:1050-1061`; FAQ docs.iroh.computer: «with or without a relay» [П-р]).
- Свой внешний адрес можно объявить вручную: `add_external_addr` / `Builder::external_addr` (`src/endpoint.rs:1021-1033`). Это подходит для адреса из UPnP или известного белого IP.
- TLS: только RFC 7250 raw public keys, Ed25519 (`src/tls.rs:1-6`, `src/tls/resolver.rs:66`). Сервер проверяется по ключу, зашитому в имя сервера (пиннинг по EndpointId, `src/tls/verifier.rs:33-47`).
- **Клиентский ключ сервер принимает любой** (`src/tls/verifier.rs:125-139`, «we don't check the client certificate»). Отсев не-друзей возможен только после рукопожатия хуком `after_handshake` (`src/endpoint/hooks.rs:102`). То есть незнакомец доводит рукопожатие до конца и тратит наш CPU.
- Пробивание NAT в iroh это расширение QUIC по черновику draft-seemann-quic-nat-traversal поверх **уже установленного соединения**, требует multipath (`src/endpoint/quic.rs:526-548`). В архитектуре iroh первое соединение обычно идёт через relay, потом мигрирует на прямой путь (`src/lib.rs:107-115`). **Без relay встроенный hole punching первую связь не создаёт**: первый путь должен пройти напрямую сам [В].
- Есть обмен наблюдаемыми адресами между пирами: `send_observed_address_reports` / `receive_observed_address_reports` в `QuicTransportConfig` (`src/endpoint/quic.rs:447-460`). Это и есть «адрес, полученный при прямом контакте». Значения по умолчанию не проверены.
- STUN как протокол в коде не найден [П-р]; внешний адрес iroh узнаёт через QAD/HTTPS к relay [П]. Документация: UDP 7842 к relay «Lets a device learn its own public address. This is the job STUN does» [П-р].
- Фичи по умолчанию: `metrics`, `fast-apple-datapath`, `portmapper`, `tls-ring` (`Cargo.toml:67-73`). `iroh-relay` остаётся обязательной зависимостью даже при выключенном relay [П], код клиента relay попадает в сборку. Гарантии «нет телеметрии» в документации не найдено [НП]; метрики iroh-services шлются только при подключённом клиенте с API key [П-р].
- Тест `endpoint_two_direct_only` (`src/endpoint.rs:2430-2489`) **не доказывает работу без внешних служб**: он строит endpoint через `presets::N0` и только выключает relay, а pkarr/DNS-поиск n0 при этом включён [П]. Опираться на него нельзя, нужен свой тест на `Builder::empty()`.
- Транспорт `noq` 1.3.0 от n0-computer [П-р]; является ли он форком quinn и насколько аудирован [НП].

Плюсы [В]: готовый пиннинг Ed25519 по RPK (меньше нашего кода в критичном месте), multipath и миграция путей при смене IP, обмен наблюдаемыми адресами, порт-маппер, хуки. Модель «адресация по ключу» совпадает с нашей идентичностью.
Минусы и риски [В]: архитектура рассчитана на relay; путь «без relay и без lookup» документирован (`presets::Empty`, изолированный режим [П-р]), но по умолчанию везде N0, а единственный найденный тест прямого режима идёт с N0 [П]; ошибка конфигурации (`Builder::new(N0)` вместо `empty()`) молча включает зарубежные серверы, и реальный пример этого есть: DashBeam на iroh держит обнаружение n0 неотключаемым [П-р]; код relay и DNS в сборке; незнакомец доходит до конца рукопожатия; noq менее известен, чем quinn; объём зависимостей больше.

**B. quinn 0.11.12 + rustls 0.23.45 с RFC 7250 RPK и своим верификатором.**
Что известно [П-р]: rustls реализует RPK на клиенте и сервере, даёт кастомные верификаторы; quinn-proto принимает готовый `rustls::ClientConfig`. Работа RPK поверх QUIC end-to-end [НП].
Плюсы [В]: в коде вообще нет relay и чужих адресов, соответствие требованиям 1-2 структурное, а не конфигурационное; неизвестный ключ клиента отвергается внутри рукопожатия; quinn распространён шире.
Минусы [В]: свой «клей» RPK-верификации (не криптография, но критичный код, вести architect и проверять security); свои миграция при смене IP (переподключение + докачка), обмен наблюдаемыми адресами, UPnP/PCP (`igd-next` 0.18.0 активен; `natpmp` 0.5.0 сомнителен; `pcp` 0.2.0 мёртв; `crab_nat` 0.8.1 не проверен [П-р]).

### 2.4. Решение
**Предварительно: вариант A (iroh 1.3.0, `Builder::empty()` + `Minimal`, `RelayMode::Disabled`, без address lookup), за собственным интерфейсом транспорта в ядре, чтобы замена на B стоила одного крейта.** Обоснование: BRIEF раздел 8 прямо задаёт правило «iroh, если отключение relay и discovery возможно, иначе quinn+rustls». По исходнику отключение возможно [П статически], но в работе не проверено. Поэтому выбор условный: **любой провал ворот G1-G3 ниже автоматически переключает на вариант B**, без нового обсуждения.

Моё возражение записано, а не подменено (CORE п.2): вариант B даёт структурную гарантию «нет третьих сторон» и отказ незнакомцу внутри рукопожатия, а главный плюс A (hole punching) без relay для первой связи не работает. Вопрос владельцу в U6 ниже.

**Поправка по решениям владельца (2026-10-09), выбор A/B не меняется.** Владелец: A или B решают ворота (U6). Схема U10b (2.6) меняет оценку вариантов [В, не проверено]:
- В A клиент адресует сервер по `EndpointId` (= ключ сервера), верификатор сверяет ключ с ним (`src/tls/verifier.rs:33-47` [П]); значит при одноразовом ключе сервера клиент должен знать его заранее, чего по U10b нет. Вывод владельца «U10b склоняет к B» совпадает с моим [В]; проверка: G11.
- Плюс A «готовый пиннинг Ed25519 по RPK» и «адресация по ключу совпадает с идентичностью» при U10b теряют силу: в TLS нет постоянного ключа, идентичность (ключ пары) живёт внутри канала. Хуки `after_handshake`/`before_connect` с пиннингом по id в исходном виде неприменимы [В].
- Плюс B «неизвестный ключ клиента отвергается внутри рукопожатия» тоже теряет силу: по U10b незнакомец в обоих вариантах доходит до конца TLS-рукопожатия и отсеивается после него; владелец это принял, условие: лимиты попыток с одного IP до рукопожатия (U4, G3).
- Провал любых ворот G10-G12 у A: **автоматический переход на B**, как при G1-G3 (решение владельца 2026-10-14, U23).
- **Итог этапа 7 (2026-10-15): выбран B (quinn + rustls).** A провалил G11 (одноразовый ключ сервера в API iroh 1.3.0 задать нельзя); у B все ворота PASS, кроме IPv6-части G2 (не проверена: IPv6 выключен в ядре облачной среды). Подробно `docs/SPIKE_TRANSPORT.md`.

Обязательная конфигурация A [В]: `default-features = false` и только `tls-ring` (без `metrics`; `portmapper` решить по G5); 0-RTT не вызывать; хук `after_handshake` отвергает всех не из списка друзей до чтения любого потока; хук `before_connect` разрешает только ключи друзей; фильтр входящих по частоте с одного IP до рукопожатия (в iroh есть пример `incoming-filter`, содержимое не смотрел [НП]).
Статический страж для CI (дёшево, можно в скелете): запрет в нашем коде строк `presets::N0`, `N0DisableRelay`, `RelayMode::Default`, `RelayMode::Staging`, `iroh.link`, `n0_dns`.

**Ворота и эксперименты** (сетевые и крипто: вести architect, не builder; скелет сеть не пишет, поэтому это отдельный этап «спайк транспорта» после приёмки скелета):
- **G1. Нет исходящего трафика к третьим сторонам.** Два endpoint на `Builder::empty()` в netns; nftables логирует и режет всё, кроме адреса пира, шлюза (UPnP SSDP 239.255.255.250:1900, NAT-PMP/PCP шлюз:5351, mDNS 224.0.0.251:5353 если включён); логировать DNS-запросы. Соединение + передача 60 с, смена адреса. Критерий: ноль пакетов и DNS-запросов вне списка. Тот же прогон с `portmapper` вкл/выкл.
- **G2. Прямое соединение только по `EndpointAddr { id, Ip(..) }`.** IPv4, IPv6, LAN; без lookup. Критерий: соединение есть, ошибки lookup нет. Обязательно свой тест, не `endpoint_two_direct_only`.
- **G3. Пиннинг.** Подключение к адресу пира с неверным id обрывается в рукопожатии; клиент с ключом не из списка отвергается хуком до того, как прочитан хоть один байт прикладных данных. Замер: CPU сервера под потоком рукопожатий от незнакомцев. **[U10b, НП]** При одноразовом ключе TLS пиннинг в рукопожатии не применяется (формулировка выше действовала до U10b); для A и B проверяется: соединение без верной подписи ключом пары внутри канала рвётся до первого байта прикладных данных (подробно G10); замер CPU под потоком рукопожатий от незнакомцев и работа лимита по IP до рукопожатия, для A и для B.
- G4. Одновременное открытие (оба вызывают `connect` друг к другу по известным адресам) в эмуляции NAT: EIM/EIF, EIM/адресно-ограниченный, EIM/порт-ограниченный, симметричный (EDM), CGNAT 100.64.0.0/10, двойной NAT, hairpin. Таблица «удалось / время». Нужно и для A, и для B: вывод раздела 3 опирается на это. **[посредник]** Два режима: периодические попытки без синхронизации (3.2) и синхронизированный старт с адресами, наблюдаемыми снаружи (имитация посредника скриптом, 3.4); таблица для обоих.
- G5. Порт-маппинг: `portmapper` iroh и `igd-next` против miniupnpd в netns; открытие и закрытие маппинга.
- G6. Наблюдаемый адрес от пира (`*_observed_address_reports`) совпадает с внешним адресом NAT в эмуляции.
- G7. Смена IP посреди передачи: миграция путей (A) против переподключения с докачкой (B).
- G8. Скорость: loopback и netem (задержка, потери), A против B, одинаковые окна; CPU. Никаких заявлений до замера.
- G9 (только если переход на B): RPK поверх quinn end-to-end, взаимная аутентификация, отказ неизвестному ключу внутри рукопожатия. **[U10b, НП]** Взаимная аутентификация и отказ внутри рукопожатия больше не цель. Проверяется: только TLS 1.3; сервер выдаёт новый ключ на каждое рукопожатие (резолвер ключа rustls вызывается на каждое рукопожатие [НП]); клиентский верификатор не пиннит ключ сервера, но подпись рукопожатия TLS 1.3 проверяет; клиентский сертификат не запрашивается.
- **G10 [НП]. Экспортёр TLS и аутентификация после рукопожатия (A и B).** Экспортёр ключевого материала (RFC 8446 п. 7.5) доступен на обеих сторонах QUIC-соединения (`export_keying_material` в rustls/quinn и в iroh/noq [НП]); значения совпадают у клиента и сервера и различаются между соединениями; при MITM из двух TLS-сессий различаются, и подписи не проходят. Аутентификация на первом потоке: неверная подпись, чужая пара, подпись с другого соединения, перепутанная роль, превышение таймаута, слишком длинное сообщение: соединение рвётся до первого байта прикладных данных. Нужно этапам 9 и 11 (SAS из экспортёра).
- **G11 [НП]. Одноразовый ключ сервера.** A: можно ли в iroh 1.3.0 без форка принимать соединения на одном сокете с новым ключом TLS на каждое соединение и подключаться клиентом, не зная ключа сервера заранее (по 2.3 скорее нет [В]: новый endpoint на соединение означает новый сокет, а клиент сверяет ключ с `EndpointId`). B: проверяется в G9.
- **G12 [НП]. Что видит наблюдатель.** Захват трафика соединения: Initial-пакеты QUIC расшифровываются любым наблюдателем (ключи Initial выводятся из открытых данных, RFC 9001 п. 5.2 [В]); в них и в прочем открытом трафике нет ключа пары, идентификатора пары, постоянного ключа, имени устройства; SNI и ALPN одинаковы у всех установок или пусты. Для A отдельно: не попадает ли `EndpointId` в имя сервера [НП].

### 2.5. Транспорт за интерфейсом, TCP позже (U7)
Решение владельца: в первой версии TCP не делать; транспорт за общим интерфейсом, выбор пути в слое соединения, чтобы TLS 1.3 по TCP подключить позже без переделки; диагностика «UDP недоступен» остаётся.
Следствия для плана [В]:
- Трейт транспорта (`chervo_transport::Transport`) отдаёт соединение, потоки, адрес пира и экспортёр ключевого материала TLS; аутентификации, выбора пути и знания о relay в нём нет.
- Выбор пути и транспорта (LAN, IPv6, IPv4 с UPnP, пробивание, позже TCP) делает слой соединения (`chervo-connect`).
- Аутентификация U10b стоит над транспортом и опирается только на экспортёр TLS 1.3, который есть и в TLS 1.3 по TCP (RFC 8446 п. 7.5); значит TCP-адаптер ляжет под ту же схему без её правки [В].
- Открыто (U25): миграция QUIC при смене IP и multipath iroh происходят внутри транспорта; считать ли это нарушением «выбор пути в слое соединения».

### 2.6. Аутентификация соединения: одноразовый ключ TLS + подпись ключом пары (U10b)
Решение владельца: вариант «(б) с одноразовым транспортным ключом»; держим его до результатов тестов (ворота и проверка схемы на этапе 9). Ниже схема в той мере, в какой она следует из решения; всё [В], ничего не запускалось, спецификацию пишет architect на этапе 9, ревью architect и security.
1. Каждое соединение: TLS 1.3 (QUIC) на новом случайном ключе, созданном библиотекой; ключ не сохраняется и выбрасывается после соединения. Постоянного ключа устройства нет. Forward secrecy даёт эфемерный обмен TLS 1.3, как и раньше.
2. TLS сам по себе не аутентифицирует собеседника: ключ сервера клиент не пиннит, клиентский сертификат не запрашивается. Подпись рукопожатия TLS проверяется как обычно.
3. Сразу после рукопожатия, на первом потоке, до любых прикладных данных: звонящий называет пару и подписывает ключом пары значение экспортёра TLS этого соединения вместе с меткой домена и ролью стороны; вызываемый проверяет подпись ключом друга из своего списка и только после этого подписывает тем же образом со своей ролью; звонящий проверяет. Не совпало, нет подписи, таймаут: соединение рвётся.
4. Почему это закрывает MITM [В]: посредник в канале держит две разные TLS-сессии, у них разные значения экспортёра, и подпись с одной стороны не подходит к другой.
5. Порядок «сначала звонящий» выбран, чтобы вызываемый ничего не раскрывал неаутентифицированному (BRIEF раздел 7) [В]. Цена [В]: звонящий раскрывает идентификатор пары тому, кто ответил по адресу (по устаревшему адресу это может быть чужое устройство); наблюдатель (DPI) его не видит, канал уже зашифрован. Это расходится с буквой BRIEF раздел 3 «аутентификация до обмена любыми метаданными» (U26). Как назвать пару, не раскрывая стабильного идентификатора (например, вызываемый перебирает ключи своих друзей вместо идентификатора), решает спецификация этапа 9; отход от формулировки владельца «звонящий называет пару» только с его согласия.
6. Только стандартный экспортёр TLS и подпись Ed25519 библиотекой; своей криптографии нет. Подпись идёт в отдельном домене (тег, не совпадающий с контекстом подписи TLS); ключ пары в самом TLS не используется (это снимает замечание Н3 из ревью этапа 10 экспериментальной ветки [В]).
7. DoS: незнакомец доходит до конца TLS-рукопожатия (принято владельцем); меры: лимит попыток с одного IP до рукопожатия, адресная валидация QUIC (Retry), таймаут и лимит размера сообщений аутентификации, одна попытка на соединение. Замер: G3.
8. Плюсы по владельцу: проверка подлинности в одном месте (при проблемах с шифрованием меняется только TLS); наблюдатель не видит ни метки пары, ни постоянного ключа (проверка G12); один порт; ключи по парам сохраняются.
9. Следствие для A/B: склоняет к B [В, вывод владельца и мой], окончательно решают ворота (G1-G12, 2.4).

### 2.7. Ключи пар и хранилища (U10a-2, U10c)
- **Ключ Ed25519 на каждую пару друзей** (U10a-2 п.3), создаётся явным шагом при добавлении друга, известен только этой паре. Следствия [В]: токен приглашения подписан новым ключом пары (подпись доказывает только владение, подлинность даёт SAS, BRIEF раздел 3); токен обновления адреса отдельный на каждого друга, подписан ключом этой пары, счётчик против replay свой на пару; список друзей хранит идентификатор пары, публичный ключ друга и наш публичный ключ пары (несекретная метка); в хранилище ОС одна запись на пару, всего друзья плюс незавершённые приглашения. Вопрос «как сервер выбирает свой ключ до того, как узнал клиента» снят U10b: в TLS ключ одноразовый, ключ пары подписывает только внутри канала.
- Ключ **никогда не создаётся молча**: только при добавлении друга и по кнопке «пересоздать ключ». «Записи нет», «хранилище заблокировано», «хранилище недоступно» различаются; ключ пропал или не совпал с меткой: ошибка и предложение добавить друга заново (U10a-2 п.5).
- **Копии связки средствами пользователя допустимы** (U10a-2 п.1); приложение само ключ не копирует, не экспортирует и никуда не передаёт.
- **Хранилища:** Windows Credential Manager, macOS login keychain, Linux Secret Service. На Linux база gnome-keyring в фоне, в том числе без рабочего стола (мини-ПК владельца), разблокировка паролем после перезагрузки, например по ssh (U10c п.1); как именно запускать и разблокировать демон без сессии рабочего стола [НП]. keyutils ядра отклонён (U10c п.2). Привязка к TPM/Secure Enclave в первую версию не входит (U10a-2 п.4).
- **Режим «локальные ключи»** (U10c п.3): файл, зашифрованный паролем пользователя (растяжение пароля + AEAD, проверенные библиотеки; крейты и параметры выбирает architect на этапе 10 по исходникам версии, ревью security). Только по явному выбору пользователя, не по умолчанию и никогда как молчаливая замена недоступному хранилищу ОС. При включении приложение прямо пишет о рисках: стойкость зависит от пароля (офлайн-перебор украденного файла), вредонос может перехватить ввод пароля, забытый пароль = повторное добавление друзей, файл попадает в бэкапы. В коде: ещё одна реализация того же трейта хранилища, что и хранилища ОС [В].
- **Кража ключа вредоносом под тем же пользователем** (U10a-2 п.2): хранилища ОС от этого, по всей видимости, не защищают (на macOS возможен запрос доступа) [В/НП, таблица силы защиты по ОС в спецификации этапа 10 экспериментальной ветки, в main не перепроверена]. Меры: автоприём выключен по умолчанию, приём только с подтверждением, предупреждение об исполняемых типах, «пересоздать ключ», уведомление друзей (отзыв, подписанный старым ключом пары; новый ключ только через повторное добавление со SAS). Украденный ноутбук: защиты нет, только пересоздание ключей и повторное добавление.
- **Linux без Secret Service:** установщик проверяет его наличие, при отсутствии понятно сообщает и предлагает установить; молча не работать без него и не подменять файловым хранилищем (OWNER_DECISIONS «Платформы и установка»).
- Справочно (спецификация этапа 10 экспериментальной ветки, в main не перепроверено [НП]): мета-крейт `keyring` 4.2.0 сам выбирает хранилище по умолчанию; там предложено брать `keyring-core` и платформенные крейты явно. Ответ на U10 по исходникам выбранной версии даёт этап 10.

### 2.8. Сохранность контента
Требование BRIEF раздел 6 (подтверждено владельцем): фото, видео, аудио доставляются побайтно идентичными. Следствия для этапа передачи [В]:
- Никакого перекодирования, пережатия, правки метаданных внутри файла. Сжатие допустимо только без потерь, только на уровне транспорта (распаковывается до исходных байтов) и только при выигрыше.
- Хэш каждого блока (хэш-дерево, библиотекой) и хэш всего файла. Несовпавший блок перекачивается и на диск под итоговым именем не пишется.

- Скорость важна, но при конфликте целостность важнее.

## 3. Открытый вопрос BRIEF раздел 5: внешний адрес и NAT без STUN и сервера

### 3.1. Откуда устройство может узнать свой внешний адрес
1. **Адреса своих интерфейсов** [В]. Глобальный IPv6 на интерфейсе обычно и есть внешний (NAT66 редок). Белый IPv4 на интерфейсе тоже. Частный IPv4 (RFC 1918) или 100.64.0.0/10 значит NAT или CGNAT.
2. **UPnP IGD / NAT-PMP / PCP у шлюза** [В]. Даёт WAN-адрес роутера и проброс порта. Работает, только если на роутере включено. Если WAN-адрес сам частный или из 100.64.0.0/10, значит двойной NAT или CGNAT: проброс на домашнем роутере снаружи не поможет, и приложение должно так и сказать.
3. **Наблюдаемый адрес при прямом контакте с другом** [В]. Когда связь уже есть (LAN, IPv6, у одной стороны белый IP или проброс), друг после аутентификации сообщает, с какого ip:port он нас видит. Это допустимо по BRIEF раздел 4 («адрес, полученный при прямом контакте»). Ограничения: это подсказка, не истина (друг может соврать, принимать только от аутентифицированного друга); полезна для третьих пиров только при endpoint-independent mapping; живёт, пока жив маппинг NAT. **Владелец разрешил (U6, вариант 5):** только как подсказка с проверкой, не принимать слепо.
4. **Адрес из токена друга** [В]. Это адрес друга, а не наш. Для IPv4 за NAT он верен, только если в токене проброшенный порт (UPnP/PCP) или NAT сохраняет порт и маппинг ещё жив.
5. **Наблюдаемый адрес от сервера-посредника** (только с согласия пользователя, 3.4) [В]. То же, что п.3, но от нашего сервера. При симметричном NAT (EDM) годен только для пути к самому посреднику.

Общий друг адреса других друзей не раздаёт: владелец запретил (U6, вариант 6).

### 3.2. Пробивание NAT без сервера
Hole punching требует, чтобы обе стороны знали внешний ip:port друг друга и слали пакеты одновременно [В]. Без сигнального сервера «одновременно» достигается только так: пока приложение открыто, оно периодически (каждые несколько секунд, окно десятки секунд) шлёт QUIC Initial по всем последним известным адресам всех друзей. Когда оба онлайн, попытки перекрываются. Порт берётся из токена, из прошлого прямого контакта или из UPnP/PCP. Встроенный hole punching iroh тут не помогает: ему нужно уже установленное соединение (раздел 2.3) [В]. Работает ли схема и на каких NAT, это G4.

С посредником (только по согласию, 3.4) «одновременно» достигается синхронизацией момента старта, а адреса берутся свежими, наблюдаемыми посредником [В]. Сравнение двух режимов: G4.

### 3.3. Что НЕ получится (честно)
- **Симметричный NAT (endpoint-dependent mapping) у обеих сторон**: нет [В]. Внешний порт для нового адресата заранее неизвестен. Посредник это не решает (3.4).
- **Симметричный у одной стороны + порт-ограниченная фильтрация у другой**: как правило, нет [В]. Против EIM с адресной фильтрацией или белого IP может пройти, если другая сторона знает IP первой.
- **CGNAT у обоих**: часто нет [В]. Зависит от того, сохраняет ли CGNAT оператора endpoint-independent mapping; поведение российских операторов [НП], у мобильных [Д: часто симметричный]. Проброс через UPnP на домашнем роутере за CGNAT не помогает [В]. PCP к самому CGNAT почти никогда не доступен абоненту [Д]. Посредник помогает, только если CGNAT сохраняет EIM [В].
- **Оба за одним CGNAT** без hairpinning: нет [В].
- **UDP заблокирован или срезан (ТСПУ)**: QUIC не работает вовсе [В]. TCP-запасного пути в первой версии нет (U7, решение владельца); транспорт держится за интерфейсом, чтобы добавить TCP позже (2.5).
- **У обоих сменился IP, стабильного адреса нет**: друг друга не найдут, пока один не передаст токен вручную (BRIEF раздел 4) [В]. С посредником (по согласию) найдут, если прямой путь затем пробивается.
- **Тип NAT без внешнего отражателя надёжно не определить** [В]. Частично: WAN-адрес из UPnP выдаёт CGNAT/двойной NAT; разные наблюдаемые порты от двух разных друзей выдают симметричный NAT. Поэтому объяснение пользователю будет «насколько удалось определить», а не точный диагноз.
- **Предсказание портов / «birthday»-пробивание симметричного NAT** не планируется [В]: успех вероятностный, сотни пакетов похожи на сканирование и могут привлечь DPI. Это не обход, а лотерея; в план не включаем (U8).
- **IPv6**: NAT обычно нет, но домашний роутер держит stateful firewall и режет входящие; одновременное открытие тем же приёмом обычно проходит [В]. Временные адреса (privacy extensions) меняются, адрес в токене может устареть за сутки [В]. Доля IPv6 у российских провайдеров [НП].

### 3.4. Сервер-посредник для поиска (требование 3, решение владельца 2026-10-09)
Что делает [В]:
- Программа наша, хост любой (свой компьютер, мини-ПК, арендованный сервер). Используется только с явного согласия пользователя: когда прямой путь не найден (например CGNAT), приложение сообщает «вы за CGNAT, к вам не достучаться напрямую» и спрашивает, использовать ли посредника.
- С согласия устройство держит регистрацию у посредника; посредник видит его наблюдаемый внешний ip:port. Когда сторона пары хочет соединиться, посредник сообщает обеим текущие адреса друг друга и общий момент старта; обе одновременно шлют QUIC Initial друг другу. Соединение дальше прямое и аутентифицируется по U10b.
- Файлы и ключи через посредника не идут никогда, пересылки трафика (relay) нет: в протоколе посредника нет сообщения «переслать данные», размер и частота сообщений жёстко ограничены (проверяется на этапе 13б).

Чем помогает [В, проверить G4 и этапом 16]: синхронизация вместо периодических попыток; свежие адреса после смены IP у обоих; CGNAT с одной стороны, если он сохраняет EIM, а другая сторона не симметричная.

Что НЕ решает [В]: симметричный NAT (EDM) у обоих; CGNAT у обоих при EDM; симметричный у одной стороны + порт-ограниченная фильтрация у другой (как правило); оба за одним CGNAT без hairpinning; блокировку UDP; недоступность самого посредника. Тогда приложение честно говорит «прямое соединение невозможно» и что можно сделать. Relay нет.

Безопасность: посредник видит адреса, время и факт соединения пары; владелец этот риск принимает (сервер наш), отдельных мер не требуется. Подмена адресов посредником ведёт только к отказу соединения: чужой собеседник не пройдёт подпись ключом пары (U10b) [В]. Как пары находят друг друга у посредника (идентификатор встречи) и как посредник защищается от DoS, решает спецификация этапа 13б. Посреднику нужен публично доступный адрес (белый IP или проброс порта) [В]; подходит ли мини-ПК владельца, зависит от его подключения [НП]. Вопросы о согласии и адресе посредника: U24.

## 5. Блокирующие неопределённости (для `docs/OPEN_QUESTIONS.md`)

Формат: вопрос, консервативное решение, почему. Ниже формулировки этапа 0 без изменений; статусы после решений владельца (U6, U7, U10, U10b, U10c, U18 и новые U23+) в `docs/OPEN_QUESTIONS.md`.

- **U1. Шлёт ли iroh на `Builder::empty()` что-либо третьим сторонам во время работы?** Решение: считать «не доказано» до G1; при провале G1 переход на B. Почему: требование 2 жёсткое, статическое чтение кода не равно проверке.
- **U2. Устанавливается ли соединение только по прямым адресам без lookup?** Решение: G2 до любой логики поверх транспорта. Почему: единственный тест апстрима на это идёт с пресетом N0.
- **U3. На каких NAT работает одновременное открытие без сигнального сервера?** Решение: обещать пользователю только LAN, IPv6, белый IP и UPnP; hole punching IPv4 помечать «может не сработать» до таблицы G4. Почему: без замера заявлять нельзя.
- **U4. Незнакомец в iroh доводит рукопожатие до конца (клиентский ключ не проверяется).** Решение: хук `after_handshake` + лимит по IP до рукопожатия + адресная валидация QUIC; если G3 покажет неприемлемую нагрузку, переход на B, где отказ внутри рукопожатия. Почему: BRIEF раздел 7, DoS и «не раскрывать информацию неаутентифицированным».
- **U5. noq: отношение к quinn, аудит, сопровождение.** Решение: принять как риск цепочки поставок, держать транспорт за своим интерфейсом, `cargo audit` + SBOM. Почему: первоисточники недоступны.
- **U6. Можно ли использовать друга как отражатель собственного адреса (вариант 5) и как раздатчика адресов общих друзей (вариант 6)?** Решение: вариант 5 разрешить только как подсказку от аутентифицированного друга при прямом контакте; вариант 6 не делать до ответа владельца. Почему: 5 прямо подпадает под «адрес, полученный при прямом контакте», 6 вводит третье устройство в путь обнаружения и раскрывает IP. Там же вопрос владельцу: A (iroh) или B (quinn) при прохождении ворот, с учётом возражения из 2.4.
- **U7. Нужен ли прямой TCP-запасной путь (TLS 1.3 по TCP с пиннингом), если UDP режут?** Решение: в MVP не делать, диагностировать «UDP недоступен» и сказать прямо. Почему: не нарушает требований, но расширяет объём и поверхность атаки; решать владельцу.
- **U8. Пробивание симметричного NAT угадыванием портов.** Решение: не делать. Почему: вероятностно, похоже на сканирование, может спровоцировать DPI.
- **U9. Что анонсировать в mDNS.** Решение: не публиковать в LAN публичный ключ и имя устройства; анонс без идентичности (или метка, понятная только друзьям), аутентификация уже в QUIC. `iroh-mdns-address-lookup` 0.6.0 не брать, пока не прочитано, что он публикует [НП]. Почему: открытый ключ в LAN = отслеживание устройства.
- **U10. Хранение приватного ключа.** iroh и rustls подписывают ключом в памяти процесса; хранилище ОС (`keyring` 4.2.0) хранит байты, а не подписывает само [В]. Решение: ключ в хранилище ОС, в память только на время работы, обнуление при выходе; на macOS запретить синхронизацию в iCloud Keychain, на Windows не попадать в бэкап. Умеет ли это `keyring` [НП]. Почему: BRIEF раздел 3 «не попадает в бэкапы».
- **U11. 0-RTT и возобновление сессий.** Решение: 0-RTT не использовать, тикеты отключить (можно ли `max_tls_tickets` = 0 и отключить тикеты на сервере [НП]). Почему: forward secrecy и replay.
- **U12. IPv6-адреса в токене и утечка IP.** Решение: в токен класть только нужные адреса, временные IPv6 помечать как короткоживущие; вопрос в `THREAT_MODEL.md`. Почему: BRIEF раздел 7, «утечка IP через токен».
- **U13. Критерий этапа 2 по аналогам выполнен не полностью** (нет доступа к GitHub и сайтам). Решение: зафиксировать как невыполненную часть критерия; на выбор не влияет, так как форка нет. Перепроверить при появлении доступа. Почему: CORE п.4, не выдавать непроверенное за проверенное.
- **U14. Порт-маппер.** Решение: включать UPnP/PCP по BRIEF раздел 5, закрывать маппинг по окончании передачи; если G5 покажет обращения куда-либо кроме шлюза, отключить `portmapper` iroh и взять `igd-next`. Почему: требование 2.
- **U15. Скорость iroh/noq против quinn.** Решение: не заявлять, решать по G8. Почему: замеров нет.
