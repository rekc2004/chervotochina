# Флак `no_leaks_full_scenario` (2026-10-23)

## Симптом
`crates/chervo-receive/tests/no_leaks.rs` `no_leaks_full_scenario` падает примерно в 2% прогонов под нагрузкой CPU:
- CI ubuntu на `d20fd76` упал один раз, перезапуск прошёл.
- Linux-машина владельца: 3 падения из 150 обычных прогонов и 11 из 450 прогонов по 3 параллельно, оба замера во время сборки. В простое 0 из 500.
- Windows, 6 параллельно: 4 падения из 75.

Проявления:
- отправитель завершается `Failed { reason: Protocol }` (no_leaks.rs:625);
- `timed out waiting for OfferReceived` (no_leaks.rs:335);
- `offer is waiting` (no_leaks.rs:583).

## Причина (проверено временной диагностикой, в репозиторий не вошла)
1. После приглашения оба движка звонят друг другу в один такт. У X своё соединение id=3, у Y принятое id=4: это одно и то же QUIC-соединение.
2. Своё соединение Y (id=5) выигрывает по правилу дублей («меньший caller_pub выигрывает», `new_wins=true`, вероятность около 50/50 из-за случайных ключей). Y закрывает id=4, и у X оно приходит как `ApplicationClosed(1)` (CLOSE_DUPLICATE) на id=3.
3. Ещё 1-5 мс `engine.connection()` у X возвращает уже закрытое id=3. Движок публикует соединение в `live` до того, как разрешён дубль.
4. Если отправка попадает в это окно, возможны два варианта:
   - **Вариант A.** `sender_main` открывает поток на id=3, затем `attempt_lost` в `SPhase::Offering` вызывает `finish_send(Failed(Protocol))` (`sender.rs:381`). Если `open_bi` не прошёл, то же самое делает `sender.rs:558`. Повтора на новом соединении нет.
   - **Вариант B.** Предложение дошло до Y по id=4, потом id=4 закрывается как дубль, и получатель теряет ожидающую сессию.

Лог одного из падений:
```
TR sender_main conn_id=3 / open_bi done ok=true
TR attempt_lost via ctl_reader conn_id=3
PROTO-SITE sender.rs:384  (attempt_lost, SPhase::Offering)
ENG on_closed id=3 live=Some(3)
REG admit-first id=6 init=false
```

## Оценка
**Дефект продукта.** Потеря или замена соединения, пока предложение ждёт ответа, даёт `Failed(Protocol)` без повтора, и причина при этом неверная. Пользователь может встретить это при одновременном дозвоне: с таймингами по умолчанию редко, на WAN чаще. Шире второй случай: связь рвётся, пока получатель решает, принять ли файл.

**Дефект теста.** Тест отправляет сразу, как только появилось первое соединение.

Решение владельца: полный фикс по крит. схеме (этап 14б).
