# Запуск локальной сессии (Claude Code на своём компьютере)

Зачем: облачный лимит почти исчерпан (осталось ~30 $), локальный Claude Code тратит лимит тарифа, а не облачный. Разработка продолжается локально по тому же конвейеру комбайна. Результат возвращается в репозиторий обычным push, поэтому любая следующая сессия (локальная или облачная) подхватит его из `docs/TASK.md`.

## Подготовка (один раз, руками)
1. Установить: Git, Rust через rustup (https://rustup.rs). Это инструменты разработки, они разрешены владельцем. На Windows rustup сам предложит Visual Studio Build Tools (C++), их нужно поставить. Claude Code CLI или десктоп.
2. Склонировать и встать на рабочую ветку:
   ```
   git clone https://github.com/rekc2004/chervotochina.git
   cd chervotochina
   git checkout claude/hopeful-hawking-2sacz9
   ```
3. Проверить, что сборка идёт: `cargo test --workspace --locked`. Первая сборка займёт несколько минут. Версию Rust задаёт `rust-toolchain.toml`.
4. Запустить Claude Code в папке репозитория. Модель основной сессии: Sonnet (экономно). По `pipeline.md` architect тогда обязателен для спецификаций, а security для ревью критичного.

**Правило одной сессии:** одновременно работает только одна сессия (локальная или облачная). Перед началом выполнить `git pull`, после каждого этапа сделать push. Тогда не будет конфликтов.

## Промпт (вставить в новый чат целиком)
```
Прочитай CLAUDE.md, .claude/combine/CORE.md, .claude/combine/pipeline.md, затем docs/TASK.md (раздел «Состояние» и строки этапов 11-18) и docs/OWNER_DECISIONS.md. Работаешь как дирижёр комбайна в локальной сессии на компьютере владельца.

Ветка: claude/hopeful-hawking-2sacz9. Перед началом `git pull`. В main не пушить, force-push не делать.

Порядок:
1. Закрепи версию Rust в CI (.github/workflows/ci.yml и rust-toolchain.toml): CI на stable уже ломался от нового правила clippy. Выбери точную версию, которая есть локально, и проверь, что clippy и тесты проходят.
2. Дальше следующий этап по TASK.md: 12 (адреса и смена IP), затем 13 (соединение, без сервера-посредника). Учти требования, перенесённые в этап 13 из ревью этапа 11 (они записаны в TASK.md под этапом 11). Каждый этап идёт по «крит. схеме»: спецификация combine-architect, код combine-builder (sonnet, на критичном effort high), ревью combine-security. Не больше двух кругов правок, потом доклад владельцу.
3. Спорное спрашивай у владельца: он на связи. Каждый вопрос короткий, со своим рекомендуемым вариантом.
4. После каждого этапа:
   - cargo fmt --check, clippy -D warnings, cargo test --workspace --locked, scripts/check-forbidden.sh;
   - обновить docs/TASK.md (сделано, перенесено, расход);
   - commit с трейлером Co-Authored-By, затем push;
   - проверить CI на GitHub.
5. Если на этой машине нельзя запустить проверку (например стенд tools/netns требует Linux и root), так и запиши в TASK.md как «не проверено» и не выдавай это за пройденное.

Отчёт владельцу после каждого этапа: что сделано, что проверено фактически, что нет, сколько вызовов агентов.
```

## Что делать только локально (облако не может)
- Проверка на реальной сети: два стационарных компьютера, затем ноутбук в чужой сети, CGNAT. Сценарии будут после этапа 13. Результаты записывать в `docs/reports/REAL-NET-<дата>.md` и пушить.
- Ручная проверка интерфейса на Windows и macOS (этап 18).
- Подпись релизов: ключ подписи только на вашей машине, никогда в репозитории и в облаке.

## Как вернуть результат
Только через репозиторий: commit и push в `claude/hopeful-hawking-2sacz9`. Состояние держит `docs/TASK.md`. Следующая сессия, в облаке или локально, начинает с `git pull` и чтения TASK.md. Пересказ в чате не нужен.
